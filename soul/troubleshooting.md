# 排障思维

## 兵分两路（排障总原则）

排障一开始就分成两条线并行推进，不要串行：

| | 线 1：止血 | 线 2：根因 |
|---|---|---|
| 目标 | 先让业务恢复、影响不扩大 | 搞清楚为什么发生、怎么根治 |
| 关注 | 具体现象、影响面、最快的恢复手段（重启、扩容、切流、回滚、调超时/阈值） | 细节深究：时间线、对照组、日志/指标/源码，结论分「已证实 / 推断」 |
| 产出 | 止血动作 + 验证业务已恢复 | 根因结论 + 根治方案（前置条件、禁忌）+ 防复发（告警、巡检） |
| 节奏 | 快，给一套可执行方案，等用户拍板 | 不赶时间，宁可留「待核实」也不硬下结论 |

衔接要点：
- **止血前先保留现场**：重启/回滚前花几十秒抓线程栈、关键日志、指标快照，否则根因线没有证据。
- **止血不等于结束**：状态写成「已恢复，未根治」，根因线继续跟到底。
- **汇报时两条线分开写**：先写止血进展，再写根因进展。

## 根因线的通用路径

只读取证 → 多源时间线对齐（UTC/本地双标）→ 对照组锁定唯一事件 → 相关性排除候选 → 实验/源码验证 → 结论分「已证实 / 推断」。

### 模式 A：时间线对齐，并用"对照组"锁定唯一事件
**描述**：先把多源数据对齐到同一条时间轴（指标、组件日志、系统日志、人工操作记录），统一时区，UTC 和本地时间两套都标。找出"只在故障节点出现、正常节点同样出现但结果不同"的唯一事件，再看它和指标突变的先后顺序。

**案例：时序库接入层卡死、CPU 打满约 3 小时**
- **现象**：集群三个节点里有两个先后 CPU 100%，上下文切换从十几万/秒涨到数百万/秒，TCP 连接线性堆积。
- **假设**：先排除连接数问题，也排除数据库主进程问题。只重启监控代理时连接数下降，但 CPU 不变；重启接入层进程后 CPU 立即回落。所以锁定在接入层进程。
- **验证**：
  1. 先证明日志的归属：用日志中的线程号比对 `/proc/<pid>/task`，确认这批日志确实是接入层进程写的。
  2. 统计日志量：用 `awk | uniq -c` 按分钟统计日志行数，发现某一刻从每分钟 7 万行骤降到 0。
  3. 找到同一时刻有一条"清除元数据缓存"的开始日志，但统计结束日志的次数为 0；执行它的那个线程之后再没有任何输出。
  4. 对照组：第三个节点执行了同一操作，0.49 秒就正常结束，CPU 也没有异常。
- **根因**：读源码推断，清缓存要拿全局自旋锁的写锁，而带强制刷新的查询重试在持有读锁时同步等待同一个后台线程，两者形成死锁，之后所有新查询都在这把锁上空转。
- **报告写法**：
  - 结论分"已证实 / 推断"两栏，没有线程栈的部分明确标为推断。
  - 附复发处置：重启前先花 30 秒抓线程栈和 goroutine，把推断变成实证。
  - 只重启接入层，不动数据库主进程。

### 模式 B：从"被拒绝的操作"倒查云平台活动日志，追到最初的变更
**描述**：托管服务报 Failed 时，不看表面错误，用活动日志的 correlationId 把每次失败的操作串起来，往前找第一次失败；再看那次变更前后做了什么。用同类历史事件做比对，确认是不是同一类问题。全程只读，命令清单附在报告里。

**案例：托管 K8s 集群自动升级失败**
- **现象**：维护窗口内节点 OS 自动升级失败，集群状态 Failed。
- **假设**：这次升级本身没问题，问题来自更早的配置变更。
- **验证**：
  - 活动日志显示同一个"删除托管出站 IP"的操作失败过 3 次，第一次在 16 天前。
  - 那次失败前，刚新建了 NAT 网关并关联到子网，紧接着更新了集群（推断是出站类型切换）。
  - 查这个 IP 的标签：它属于托管出站 IP，但被业务 Service 复用作入口 IP，上面挂着 12 条入站规则，所以云平台拒绝删除。
  - 和另一套测试环境之前的同类事件逐项对比，现象、诱因、根因完全一致。
- **根因**：同一个公网 IP 被平台和业务同时占用。切换出站类型时平台要删它，被拒，集群卡在 Failed 状态，之后任何协调操作（包括自动升级）都会重试并再次失败。
- **延伸**：
  - 标出"已恢复，未根治"。
  - 推断出口路径和配置不一致，提示核对外部白名单。
  - 横向排查其他生产集群有没有同样隐患。
  - 补一条告警：集群 provisioningState 不是 Succeeded 就报。
  - 写明根治步骤和禁忌：标签去掉后不要再加回。

### 模式 C：IO 异常先对齐周期性任务，再用相关性排除和锁定
**描述**：看到周期性的资源尖峰，先确认是哪个进程造成的（应用自己的 IO 指标和节点磁盘指标是否一致），再把定时任务、compact、归档、补数等候选逐个拿来和时间线对齐，用相关系数排除。实测结果和理论矛盾时，记成"待现场核实"，不硬下结论。

**案例：时序库温盘每天固定时刻出现读风暴**
- **现象**：温层数据盘每天同一时刻开始持续 55～95 分钟的读风暴，600～900 MiB/s，利用率接近 100%。
- **假设和排除**：
  - 数据库进程自身的磁盘读量等于节点磁盘读量，所以是数据库在读，不是系统任务。
  - 同一时段没有 compact。
  - 归档任务不在这个时段运行。
  - 补数任务：用户本人纠正了 AI，补数读的是热数据。
- **验证**：只有一个夜间按设备做日汇总的查询任务和读风暴吻合，相关系数 0.78，两者在同一分钟结束。
- **遗留矛盾**：这个任务只读昨天的数据，理论上应该在热层。新假设是近期的数据文件也落在了温层目录，需要上机核实。
- **用户的追问方式**："不要跟我说模棱两可的，你就告诉我，这个语句条件会不会查到温层数据！""但是实际实测，会导致这个语句去扫描所有温盘数据。"

### 模式 D：区分"增长"和"策略"，把峰值与低点分开看
**描述**：容量告警先问一句：是量在涨，还是配置本身就会把盘占满？把锯齿曲线拆成"删除前峰值"和"删除后低点"两条趋势线，再用"每日删除量≈每日写入量"反推真实增量。

**案例：日志平台数据盘长期 90% 以上**
- **现象**：每天到 92～95%，逼近 ES 的只读线（flood stage）。
- **假设**：日志量在增长。
- **验证**：
  - 把 37 天的数据叠成"典型的一天"。
  - 峰值和低点都只是缓慢抬升，周与周之间的波动比趋势还大。
  - 每天固定时刻 ILM 删除一天的数据，删掉的量就等于一天的日志量。
  - 盘上始终存着整整 7 天的日志，刚好接近盘的上限。
- **根因**：主因是保留策略，不是日志量增长。
- **方案**：
  - 首选：保留期 7 天改为 6 天。
  - 对最大的几个服务单独缩短保留期。
  - 单节点上副本数改为 0，让集群恢复 green，不再掩盖真正的分片故障。
  - 告警阈值改成 94% 持续 10 分钟，避免每天都响。
  - 最后一档才是扩容。

### 模式 E：告警抖动先测"采集耗时"，用同一程序跨位置对照
**描述**：exporter Down 告警时有时无，先不怀疑目标宕机。先量 scrape 实际耗时和 timeout 的比例，再把同一个二进制放到不同网络位置跑一遍做对照，找出变量。

**案例：消息队列 exporter 告警反复抖动**
- **现象**：exporter Down 告警频繁，触发前一天以前也每天断 6～13 分钟。
- **假设**：exporter 挂了，或者 broker 有问题。
- **验证**：
  - 当天业务新建了 47 个 topic、近 900 个分区，scrape 耗时约 27 秒，而 timeout 是 30 秒。
  - 同一个二进制在同网段的机器上跑，0.7 秒完成（RTT 0.5ms 对比跨网段 16ms）。
  - exporter 的调优参数试过，无效。
- **根因**：跨网段时延乘以分区数暴增。
- **处置**：
  - 临时措施：timeout 调到 55 秒，告警 `for` 从 1m 改为 3m。
  - 顺手修正：Broker 告警引用了一个不存在的指标名，一并改掉，规则测试全部通过；改动前先备份。
  - 根治：把 exporter 迁到同网段，待决策。

### 模式 F：用"历史真实故障回放"验证告警是否有效
**描述**：评估告警时不看规则写得对不对，而是拿历史上真实发生过的故障去问"当时响了没有"。没响，就拆表达式找原因。

**案例：中间件高可用评审**
- **现象**：缓存集群在某天发生过主从切换，时序库的 leader 也换过一次，都没有收到告警。
- **假设**：切换告警规则有问题。
- **验证**：
  - 两条切换规则都是对恒为 1 的 info 指标做 `changes()`，结果永远是 0。
  - 另一条规则写成 `xxx_info != 1`，broker 宕机时这条序列直接消失，规则同样不会触发。
  - 时序库的监控和客户端入口都依赖第一个节点；规则的 NoData 设成 KeepLast，那个节点一挂就整体沉默。
- **结论**：告警只覆盖了"进程活着吗"，覆盖不到"拓扑是否还安全"。
- **后续**：
  - 拓扑检查：有两套缓存集群的 2/3 主节点集中在同一台机器上，挂这一台就整集群不可用。
  - 分级整改：按"严重性 × 影响范围"打分，拆成 P0/P1/P2 共 21 项任务，6 周排期。

### 模式 G：概念质疑先动手做实验，并追到源码 / 存储原理
**描述**：对"不能做""业界没先例"一类说法不轻信，先在测试机上复现。对存储占用这类黑盒问题，要求从源码和文件结构讲清楚。

**案例一：LVM 移除一块盘**
- **疑问**：LVM 明明可以减少一块盘，为什么从没听说过缩容磁盘？
- **实验**：
  1. 用两块盘组成 40G 的卷。
  2. 写入 30G，确保数据落到两块盘上。
  3. 删到 20G 以下。
  4. 移除其中一块 PV，验证数据迁移的可行性。
- **教训**：AI 给的填充命令把数据写进了根分区，把系统盘写满了。此后用户要求先确认写入路径和挂载点。
- **延伸**：继续追问 xfs 不支持缩小时有什么替代方案，以及数据不能停时怎么处理。

**案例二：时序库删了 100 多 GB 数据，compact 却释放不出那么多空间**
- **追问链**：
  1. 剩下的温层数据并不多，到底是什么在占用？
  2. head、sma、data、stt 各类文件分别是什么？
  3. 为什么一直在删 stt？
  4. 从源码讲清楚存储原理和空间分配机制。
  5. 落到建库参数和超级表参数：哪些能用来做生命周期管理。
- **处理原则**：用实际查询核对（`show table distributed` 等），不接受"按字段大小 × 行数"的理论估算。
