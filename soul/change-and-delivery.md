# 变更与交付习惯

**排查阶段**
- **默认只读**：排查期间全程只读，报告末尾附"本次使用的只读命令"。用用户的云账号核查时明确说"只读，不要操作"。
- **止血和根治分开**：状态写清楚"已恢复 / 已恢复未根治 / 已根治"。根治步骤写明前置条件，例如先补权限、先把 IP 分离出来，也写明禁忌，例如某个标签去掉后不要再加回。
- **复发处置前置**：复盘里附上判断依据和处置命令，并规定"重启前先抓证据"，例如线程栈、goroutine、关键日志的 grep。

**方案阶段**
- **先出方案页，确认后再动手**：方案做成可交互页面，有"现状 / 改造后"切换、故障场景矩阵，每一项都能选"同意 / 要修改 / 暂缓"，还能一键复制确认结果。用户确认后只实施批准的项，没确认的一律不动。

**规则与配置变更**
- **改之前先备份**：备份文件名带日期和原因（`.bak-YYYYMMDD-原因`）。
- **改法有讲究**：特定主机上的配置文件用 `cat >` 整体写入，不用 `sed -i` 或 `mv`。
- **上线前先查询验证**：每条新的 PromQL 都先在监控端查一遍，确认表达式有效、当前结果符合预期（例如 0 条）。规则文件配单元测试，改指标名时把测试一起改。

**验证方法**
- **正反证验证矩阵**：新特性验证时，每个正向结论都配一个对照组，而且对照组必须表现相反，否则正向结论无效。验证脚本失败时返回非 0 退出码。

**发布与升级**
- **GitOps 发布原则**：
  - "发哪个版本"的决定落在 Git 的一个 PR 上，不落在 ArgoCD 参数上。
  - CI 自动推进部署分支，运维只看 Diff、点 Sync。
  - 不要把琐碎事绕回运维身上。
  - 回滚用 History，CI 只追加提交、不 force push。
  - 提醒数据库迁移和配置中心的改动不会自动回滚。
- **升级前做依赖检查**：
  - 先看维护窗口。
  - 切换出站类型前，检查出站 IP 上还有没有入站规则。
  - 升级后手动发起一次节点镜像升级，验证链路已恢复。

**容量与新环境**
- **容量决策**：先改策略、后扩容；以实测数据为依据，给出"建议 / 最小"两档；N-1 按峰值 × 1.5 粗估并注明局限。
- **新环境交付**：
  - 照搬线上已验证的模式，版本和线上保持同一个小版本。
  - 中间件放在集群外。
  - 先排期倒推，确认 B 角。
  - 装服务端时同时装好客户端 CLI，配置不用明文的安全登录。
  - 不在记忆或文档里存密码。

**交付材料**
- 只写交付内容，不写安全发现。
- IP 写完整。
- 拓扑和公网入口这类事实要现场重新核实，不复用记忆里的旧值。
- 页面用宽布局。
- 已修复的问题直接删掉，不写修复过程。
