# 工作内容地图

> 重心：K8s / 云、可观测、网络与 Linux、CI/CD 是核心专长。时序库与数据库投入多，是因为不够熟悉、在补短板，不代表是专长。

## 1.1 Kubernetes / 云平台
负责多套公有云托管 K8s 生产集群和边缘轻量 K8s（K3s）的日常运维、升级、排障和架构验证。

- **托管集群升级失败排查**：节点 OS 自动升级失败时，用云活动日志和资源配置只读回溯根因，再出复盘报告和根治步骤。
- **出口 / 入口网络配置治理**：处理出站类型（负载均衡 / NAT 网关）切换、托管出站 IP 被业务复用为入口 IP 等问题，并核查同类隐患在其他集群是否存在。
- **镜像仓库访问控制**：确认仓库是否允许公网访问；评估按仓库路径做细粒度授权的两种方式，一种是范围映射加令牌，一种是基于云身份的角色。要求 AI 用用户的账号只读核实，不能操作。
- **GitOps / ArgoCD 排障与发布治理**：排查 CMP 插件渲染失败（开启的组件镜像 tag 为空）；解释为什么点了 Sync 集群却没变化（ApplyOutOfSyncOnly、参数钉住旧版本）；把研发的发布规范改造成"版本写进 Git、发布只点 Sync"。
- **新组件 / 新特性验证**：在测试集群验证 Gateway API（Envoy Gateway），让同一入口同时承载七层和四层流量，每条正向结论都配一组反证；也做过 Istio 验证。
- **资源优化**：托管集群的资源和成本优化（有专门的工作目录）。

## 1.2 时序库与数据库（补短板领域）
时序数据库（TDengine 3.x 集群）是近期投入时间最多的领域，原因是不够熟悉、需要边做边学。此外还管关系库和缓存、消息中间件的高可用。

- **时序库故障复盘**：接入层进程（taosAdapter）卡死、CPU 打满、连接堆积。从日志、指标一直追到源码层的锁机制。
- **慢 SQL 与执行计划**：判断一条查询会不会扫到温层（冷热分层）数据，用 strace 分析客户端性能瓶颈，把多行 SQL 压成单行便于执行。
- **自研 SQL 分析工具**：用 Go 写，零依赖。功能包括 SQL 指纹聚合、离线或在线解析 EXPLAIN、从慢查询表批量诊断并出 HTML 报告。
- **存储生命周期**：
  - 大批量 delete 很慢时，查看运行中的 SQL 进度。
  - compact 的线程数、定时执行、进度监控。
  - 删了数据却释放不出空间时，追查 stt、sma、head 等文件的占用。
  - keep、duration、trim 等建库参数怎么管理生命周期。
  - 数据盘扩容。
- **关系库**：MySQL 8.4 离线部署，同时装好客户端，用 login-path 做安全登录。
- **中间件高可用评估**：
  - Redis Cluster 的主节点分布，挂一台是否整集群不可用。
  - Kafka 单副本（RF=1）分区的比例。
  - 时序库的 N-1 容量和 leader 分布。
  - 评估后拆成分级整改计划。

## 1.3 可观测与告警
负责 Prometheus、Alertmanager、Grafana、blackbox、日志平台（EFK）这一整套，并在设计下一代告警交互。

- **告警覆盖审计**：
  - 方法是逐条故障场景过一遍，问"能不能第一时间感知"。
  - 找出过的问题包括：集群内告警没有转发、没有业务入口探测、副本告警等待太久、规则里 job 名写错、监控自身没人监控（缺 dead-man）。
- **"哑弹"规则排查**：对恒为 1 的 info 指标做 `changes()`，结果永远是 0。发现方法是回放历史上真实发生过的切换，确认当时没有告警。
- **exporter 抖动治理**：区分是采集超时还是真的宕机；调整 scrape_timeout 和规则的 `for`；修正写错的指标名；同步修好规则的单元测试。
- **日志平台容量评估**：判断磁盘长期 90% 以上是日志量在增长，还是保留策略导致的；给出能拖动参数的推演和多档建议。
- **告警交互网关设计**：
  - 保留 Alertmanager，在它后面加一层薄网关，告警以 IM 卡片推送。
  - 卡片上可以认领、静默、转派、升级，全程留审计记录。
  - AI 分析只读、必须附证据；处置动作只能从白名单选，分级确认。
- **Grafana**：面板和规则的盘点，覆盖面板 / 规则的数量统计、PromQL 有效性检查；面板数据可以作为容量和流量统计的数据源。

## 1.4 网络
- 云上出入口 IP、NAT 网关、负载均衡前端的归属关系。
- 跨网段 RTT 对采集的影响（同一个 exporter 跨网段采集 27 秒，同网段 0.7 秒）。
- 四层负载策略的验证：轮询、哈希、权重、健康检查、跨命名空间授权。
- 抓包和内核层工具：tcpdump、tshark、pwru，已沉淀在命令库里。
- Windows IIS 更换 HTTPS 证书：合成 pfx，追问导入密码的用途和后续是否还需要。

## 1.5 Linux 与存储
- LVM 移除一块 PV 的可行性，并在测试机上实际模拟：写入数据让它跨两块盘，删到阈值以下，再移除。
- xfs 不能缩容时的替代方案，以及数据不能停时怎么处理。
- 虚拟化平台热加磁盘后系统识别不到的原因。
- 用 iostat 区分 dm 设备和底层盘的 IO，用 sar 做第二数据源。
- 用 strace 看进程瓶颈。

## 1.6 容量与成本
- **设备流量用量统计**：用节点网卡 30 天的字节计数，按存量设备数折算出总量和单台每天、每月用量，作为采购依据。用户明确要求只给数据、不给评估意见。
- **磁盘容量推演**：峰值约等于保留天数 × 每日日志量；给出"改策略"和"扩容"两档。
- **N-1 容量估算**：7 天单机峰值 × 1.5，仅用于排序，仍需故障演练确认。
- **新环境容量**：用线上实测的内存、CPU 和 request 汇总，给出"建议 / 最小"两档 VM 规划。

## 1.7 新环境交付（边缘 / 工厂单元数据中心）
- 形态选型：K3s 还是 Docker Compose。依据是逐项统计 chart 参数化程度、环境变量数量、Ingress 改写规则和发布频率。
- 照搬线上模式：应用层复用线上 Helm chart，只写一份差异 values；中间件放在集群外的独立 VM。
- 离线镜像、证书、kubeconfig、ArgoCD 初始化；修改 ArgoCD 初始密码后清理残留的初始 secret。
- 监控从简但要能感知故障：故障场景 × 发现时间矩阵、入口探测、dead-man、告警路由选择。
- 排期倒推，并列出需要确认的事项（例如运维团队里要有人做 K8s 的 B 角）。
